# Stage 90 achievements

Apply `migrations/20261002000009_achievements.sql` and then `migrations/20261002000010_achievement_existing_activity.sql` after the earlier migrations. The second migration issues grants for qualifying reviews that existed before achievement triggers were installed. It is safe to retry. The migrations leave the old `achievements` table intact; its unknown legacy rows are not converted to new grants. New definitions and grants use stable keys and a year scope (`0` for lifetime). All dates and calendar boundaries use `Asia/Tbilisi`.

## Rules

An eligible rating is a `reviews` row with a score from 1 to 90 on an active release. This application stores ratings without text and written reviews in that same table. A published written review has at least 300 trimmed characters, matching the submission form. There is no separate review approval or soft delete state in the repository. The `ratings` table seen in platform statistics has no submission path or schema migration here and is not used. One release counts once for a user's distinct-release progress. Artist identity uses the release's normalized `artist_name`; linked author profiles can be absent.

Listener accounts are `user`, `author`, and `admin`; `media` accounts earn only media achievements. Listener lifetime: first valid rating, first written review, one eligible endorsement by the reviewed release's linked verified author. Listener annual: 10 distinct rated releases from at least 5 artists, and written reviews of 5 artists. Media lifetime: first written review. Media annual: written reviews of 10 artists, written reviews of 5 artists, endorsements by 3 distinct linked verified authors during the year, and written reviews of 3 artists whose releases have `is_new_name` or `is_freshman`. These newcomer flags are set during release submission and should be moderated before relying on them for competitive results.

The existing 100 community points per inserted review remain untouched. The existing release score trigger and thresholds (50/65/75/85 for ოქრო/ზურმუხტი/საფირონი/ლალი) also remain untouched. Release rating levels can change as reviews change.

Annual release awards have independent format groups: album, EP, single/track, and any other stored format. Eligible releases must be active and have `achievement_published_at` inside the year. Historical active releases receive `created_at` as a publication proxy because no earlier publication timestamp exists; inactive releases get an accurate timestamp when first activated after this migration. One latest valid review per account and release is used for award calculations. Listener's Choice requires 5 independent listener votes; Media Choice requires 3 independent media votes; Release of the Year requires both and ranks by their combined existing overall mean; Discovery of the Year requires both plus an existing newcomer flag. Each award ranks by its relevant mean, then total independent voters, then ascending release ID. A format with no qualifying release has a stored result with no winner.

## Processing and operations

Database triggers recompute affected user grants after review, author endorsement, role, verification, or release eligibility changes. Grants are unique per user, key, and year. Issuance and revocation are audited. The private `my_achievement_progress(year)` RPC computes progress directly from source records and only returns the authenticated user's data.

`finalize_annual_release_awards(year)` can only run after the Tbilisi year ends. It persists one result per award and format, including the score, independent voter counts, title/artist snapshot, rule version, and audit record. Repeated runs leave final results unchanged. An admin may call `finalize_annual_release_awards(year, true, 'reason')` to correct results; the previous row is retained in the audit table. A daily `pg_cron` job is registered if the extension is available. If not, register a production scheduler that runs `select public.finalize_annual_release_awards(extract(year from now() at time zone 'Asia/Tbilisi')::integer - 1);` daily. The function checks the Tbilisi calendar itself, so the scheduler's local timezone does not determine eligibility. The scheduler must run as the database owner.

The second migration automatically reconciles existing reviews. For later repairs, run `select public.reconcile_achievements(2026, 2026);` with a database owner connection, or call it as an authenticated admin. This is safe to repeat. Choose earlier years only when review timestamps and release flags are reliable. It does not invent historical annual winners. Earned dates are derived from the first source event that completed each threshold. Do not manually finalize historical years without reviewing publication dates.

The SQL migration and RPC require a running Supabase PostgreSQL instance for validation. The local checkout has no PostgreSQL, Supabase CLI, or test database, so database integration tests must run against a deployed or local Supabase project before enabling the page. Keep the Achievements tab in maintenance mode until the migration and scheduler are verified.
